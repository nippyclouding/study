# 게시판 프로젝트 수정 사항

현재 프로젝트를 검토한 결과를 우선순위별로 정리한 문서입니다.

## 우선 수정할 문제

### 1. 게시판 목록의 MyBatis 매핑 확인

`BoardMapper.xml`의 `findMainBoardsByPaging` 쿼리에 `BOARD_ID`가 추가된 것은 올바른 방향이다. 다만 현재 설정에는 DB의 snake case 컬럼명을 Java의 camelCase 필드명으로 변환하는 설정이 없다.

- `BOARD_ID` → `boardId`
- `BOARD_TITLE` → `title`
- `BOARD_WRITER_NAME` → `writerName`
- `CREATED_AT` → `createdAt`

따라서 목록 전용 `resultMap`을 사용하거나 다음 설정을 추가해야 한다.

```properties
mybatis.configuration.map-underscore-to-camel-case=true
```

명시적인 매핑을 원한다면 다음과 같이 작성할 수 있다.

```xml
<resultMap id="mainBoardResultMap"
           type="com.example.board.board.domain.Board">
    <id property="boardId" column="BOARD_ID"/>
    <result property="title" column="BOARD_TITLE"/>
    <result property="writerName" column="BOARD_WRITER_NAME"/>
    <result property="createdAt" column="CREATED_AT"/>
</resultMap>

<select id="findMainBoardsByPaging"
        resultMap="mainBoardResultMap">
    SELECT
        BOARD_ID,
        BOARD_TITLE,
        BOARD_WRITER_NAME,
        CREATED_AT
    FROM BOARDS
    WHERE DELETED_AT IS NULL
    ORDER BY CREATED_AT DESC
    LIMIT #{pagingCount}
    OFFSET #{offset}
</select>
```

### 2. 비밀번호 저장 방식 개선

현재 비밀번호를 salt 없는 SHA-256으로 저장하고 있다. 특히 비밀번호가 4자리이므로 전수조사에 취약하다.

- BCrypt, Argon2 또는 PBKDF2 사용 권장
- 같은 비밀번호라도 다른 해시가 나오도록 salt가 적용되어야 함
- 비교할 때 직접 해시 문자열을 비교하지 말고 password encoder의 `matches` 기능 사용 권장

### 3. 게시글 수정 시 비밀번호 역할 분리

현재 수정 요청에는 비밀번호가 두 군데 존재한다.

- 요청 파라미터의 `rawPassword`: 기존 비밀번호 확인
- `BoardRequestDto.password`: 수정 후 DB에 저장되는 비밀번호

변수명을 `rawPassword`로 바꾼 것만으로는 기존 비밀번호와 새 비밀번호의 역할이 충분히 구분되지 않는다. 비밀번호 변경 기능이 아니라면 생성 DTO와 수정 DTO를 분리하고, 수정 쿼리에서 `BOARD_PASSWORD`를 제외하는 것이 좋다.

```java
public class BoardUpdateRequestDto {
    @NotBlank
    private String title;

    @NotBlank
    private String writerName;

    @NotBlank
    private String content;
}
```

수정 요청의 인증용 비밀번호는 용도를 명확히 알 수 있도록 `currentPassword` 같은 이름을 권장한다.

```java
@PostMapping("/{boardId}/edit")
public ResponseEntity<Void> editBoard(
        @PathVariable Long boardId,
        @RequestParam String currentPassword,
        @Validated @ModelAttribute BoardUpdateRequestDto dto
) {
    boolean updated = boardService.updateBoard(boardId, dto, currentPassword);

    if (!updated) {
        return ResponseEntity.badRequest().build();
    }

    return ResponseEntity.ok().build();
}
```

비밀번호를 변경하지 않는 수정 쿼리는 다음과 같이 구성할 수 있다.

```xml
<update id="updateBoard">
    UPDATE BOARDS
    SET BOARD_TITLE = #{board.title},
        BOARD_WRITER_NAME = #{board.writerName},
        BOARD_CONTENT = #{board.content}
    WHERE BOARD_ID = #{boardId}
      AND DELETED_AT IS NULL
</update>
```

비밀번호 변경 기능이 필요하다면 `currentPassword`와 `newPassword`를 별도로 정의해야 한다.

### 4. 없는 게시글의 HTTP 상태 코드 수정

현재 다음 코드는 상태 코드 404가 아니라 `200 OK`와 본문 숫자 `404`를 반환한다.

```java
return ResponseEntity.ok(404);
```

실제 404 응답은 다음처럼 반환해야 한다.

```java
@GetMapping("/{boardId}")
public ResponseEntity<Board> getDetailBoard(@PathVariable Long boardId) {
    Board board = boardService.getBoardDetail(boardId);

    if (board == null) {
        return ResponseEntity.notFound().build();
    }

    return ResponseEntity.ok(board);
}
```

또는 다음과 같이 줄일 수 있다.

```java
return ResponseEntity.ofNullable(boardService.getBoardDetail(boardId));
```

### 5. 수정 실패 상태 코드 구분

현재 게시글 수정 실패는 모두 `500 Internal Server Error`로 처리된다. 하지만 실패 사유를 구분해야 한다.

- 비밀번호 불일치: `400 Bad Request` 또는 `403 Forbidden`
- 게시글 없음: `404 Not Found`
- 예상하지 못한 서버 또는 DB 오류: `500 Internal Server Error`

서비스에서 단순 `boolean`만 반환하면 실패 원인을 알기 어렵다. 예외나 결과 enum을 사용하면 컨트롤러에서 상태 코드를 구분하기 쉽다.

### 6. 페이지 번호 검증

`currentPage`가 음수이면 음수 `OFFSET`이 만들어질 수 있다. 매우 큰 값은 `int` 곱셈 오버플로 가능성도 있다.

- `currentPage >= 0` 검증
- 필요하면 offset 계산에 `long` 사용
- 잘못된 페이지 값에는 `400 Bad Request` 반환

### 7. 댓글 정렬 순서 지정

게시글 상세 조회 쿼리에 댓글 정렬 조건이 없다. DB 실행 계획에 따라 댓글 순서가 달라질 수 있으므로 다음과 같은 정렬 조건을 추가하는 것이 좋다.

```sql
ORDER BY c.CREATED_AT ASC
```

### 8. 삭제 서비스의 불필요한 조회

`BoardService.deleteBoard`에서 다음 조회 결과를 사용하지 않는다.

```java
Board findBoard = boardMapper.findBoardById(boardId);
```

게시글 존재 여부를 확인하려는 목적이라면 실제 검증에 사용하고, 그렇지 않다면 불필요한 조회이므로 제거한다.

### 9. 비밀번호 null 처리 및 DB 제약조건

다음 코드는 DB의 비밀번호 값이 `NULL`이면 `NullPointerException`이 발생할 수 있다.

```java
findBoard.getPassword().isEmpty()
```

null-safe 검사를 사용하고, DB에도 `NOT NULL` 제약조건을 설정하는 것이 좋다.

```java
if (findBoard == null || findBoard.getPassword() == null
        || findBoard.getPassword().isBlank()) {
    return false;
}
```

또한 저장소에 테이블 구조를 재현할 `schema.sql`이나 마이그레이션 파일이 없다. Flyway, Liquibase 또는 최소한 `schema.sql` 추가를 권장한다.

### 10. 요청 데이터 형식 확인

현재 컨트롤러는 `@ModelAttribute`를 사용하므로 form-data 또는 URL-encoded 형식을 전제로 한다. JSON REST API가 목적이라면 다음 형태를 검토한다.

```java
public ResponseEntity<?> createBoard(
        @Valid @RequestBody BoardRequestDto dto
)
```

HTML form 요청이 목적이라면 현재 `@ModelAttribute` 방식을 유지해도 된다.

### 11. DTO 길이 및 형식 검증

현재 제목, 작성자, 내용에는 `@NotBlank`만 있다. DB 컬럼 길이를 초과하면 DB 예외가 발생할 수 있으므로 `@Size(max = ...)`를 추가하는 것이 좋다.

비밀번호가 숫자 네 자리여야 한다면 `@Length(min = 4, max = 4)`만으로는 `abcd`도 허용된다.

```java
@NotBlank
@Pattern(regexp = "\\d{4}")
private String password;
```

### 12. HTTP 메서드와 생성 상태 코드

REST API 형태로 구성한다면 다음 구조를 고려할 수 있다.

- 생성: `POST /boards` → `201 Created`
- 수정: `PUT` 또는 `PATCH /boards/{boardId}`
- 삭제: `DELETE /boards/{boardId}`
- 상세 조회: `GET /boards/{boardId}`

### 13. 의존성 버전 관리

Spring Boot 부모 버전은 `4.0.8`인데 validation starter에는 `4.0.1`이 직접 지정되어 있다. Spring Boot starter의 버전은 부모 BOM에 맡기고 직접 지정한 `<version>`을 제거하는 것이 안전하다.

### 14. 테스트 보강

현재 테스트는 컨텍스트 로딩 테스트만 존재한다. 다음 항목에 대한 테스트가 필요하다.

- 목록 조회 시 `boardId`, 제목, 작성자, 작성일 매핑
- 정상 및 음수 페이지의 offset 계산
- 존재하지 않는 게시글 상세 조회 시 404
- 비밀번호 일치와 불일치
- 수정 시 기존 비밀번호가 의도치 않게 변경되지 않는지
- 게시글 삭제 시 댓글도 함께 soft delete 되는지
- 요청 validation 실패
- 상세 조회 시 여러 댓글이 정상 조립되는지

## 실행 환경 확인

프로젝트의 `pom.xml`은 Java 21을 요구하지만 현재 터미널은 Java 8을 사용하고 있어 테스트가 컴파일 전에 실패한다.

```text
class file has wrong version 61.0, should be 52.0
```

`JAVA_HOME`과 `PATH`를 JDK 21로 맞춘 후 다음 명령으로 다시 검증해야 한다.

```powershell
.\mvnw.cmd test
```
